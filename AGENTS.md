# AGENTS.md

Notes for AI agents working in this repo. Keep entries terse; only record what code/docs can't tell you.

## Project
Clutch Marks — Cambridge IGCSE/AS/A2 revision platform (Vite + React + TS + Supabase). Six subjects: Maths 0580/9709, Physics 0625/9702, Chemistry 0620, Biology 0610, CS 0478/9618, and English (Cambridge 0500 First Language, OxfordAQA 9280 ESL). Copy that enumerates subjects is generated from `frontend/src/lib/subjectCatalogue.ts` — see Content conventions. The live Supabase DB is production — treat it as such.

## Environment & commands
- No Supabase CLI. All SQL goes through the Management API: `POST https://api.supabase.com/v1/projects/{REF}/database/query` with Bearer token `sbp_…` (read from `.freebuff/get-keys.cjs`); project ref + anon key come from `.env` (`VITE_SUPABASE_PROJECT_ID`, `VITE_SUPABASE_PUBLISHABLE_KEY`). Service key: `GET /v1/projects/{REF}/api-keys`.
- Use the bundled Bun, not npm: `BUN="$LOCALAPPDATA/Programs/@codebufffreebuff-desktop/resources/bun/bun.exe"`. Typecheck: `"$BUN" node_modules/typescript/bin/tsc --noEmit -p tsconfig.app.json`. No CI exists.
- Apply a SQL/migration file with a rollback dry run first: `node .freebuff/apply-sql-file.cjs <file.sql> [--apply]` (the live DB needs this; there is no Supabase CLI). `.freebuff/probe-*.sql` + `.freebuff/probe-*-live.cjs` are the read-only/live verifiers for each feature.
- Database backup/restore: `npm run backup:db` dumps every `public` table via the Management API, encrypts the bundle (AES-256-GCM, `BACKUP_PASSPHRASE`) and uploads it to an S3-compatible bucket; `npm run restore:db -- <file> --verify|--to-sql` checks the manifest hashes and emits SQL. The project has **no PITR and no Supabase-side backups**, the bundle **includes `auth.users` and `auth.identities`** (added 2026-10-30: 60 users, 35 with a bcrypt hash, and the 27 Google identities — sessions and refresh tokens are deliberately left out so a restore cannot hand out live logins), though auth *configuration* still lives in the dashboard, and the script exits `2` rather than report success while off-site is unconfigured. `node .freebuff/probe-db-restore.cjs <file>` proves a restore into a scratch schema. Runbook: `docs/database-backup-and-restore.md`.
- Secret scanning runs at commit time: `.githooks/pre-commit` (gitleaks over the staged diff) is activated per clone with `git config core.hooksPath .githooks`. It exits `2` and still blocks when gitleaks is missing — install it rather than reaching for `--no-verify`. It does not scan history; `docs/pre-commit-secret-scan.md` covers install, bypasses and limits.
- **Git history was rewritten on 2026-10-30** to drop a committed session credential (`.freebuff-tmp/palette-session.json`) and the anon-key build artifacts (`production/`, `dist-single/`): `main` `072bcc9` → `958032c`, 284 commits across every ref including the 20-snapshot `refs/backups/daily` chain, then reflog-expired and gc'd so `git fsck --unreachable` is 0. **Re-clone rather than pull** — pulling the old history merges the blobs straight back. `.env.production` stays tracked on purpose (public build-time config); the key it carries is served to every browser anyway, so RLS and the revoked `anon` grants are the control, not history editing. Since `06b0776` that key is the **modern publishable key** (`sb_publishable_…`), not the legacy anon JWT — and the value a Vercel build actually reads is the **Vercel project env** `VITE_SUPABASE_PUBLISHABLE_KEY` (Vite will not let a `.env` file override an existing process env), so a live key change means the Vercel var, not just the tracked file. `.gitleaks.toml` allowlists that one public line; the rest of the ruleset is untouched and a high-entropy canary still fails the scan. `gitleaks git --log-opts=--all` is the check: it must report no `role=authenticated` JWT. The pre-rewrite tree survives only as `.freebuff-tmp/pre-purge.bundle` (gitignored, and it still contains the token — delete it once the app is confirmed working).
- Tests: `"$BUN" node_modules/vitest/vitest.mjs run` (vitest only collects `frontend/src/**/*.test.ts`). `frontend/src/lib/domainGuard.test.ts` fails on any tracked file matching `/clutchmarks\.com/i` outside its reasoned `EXEMPTIONS` list — the legacy `production/` bundle and `public/downloads/*.pdf` are exempt as generated artifacts (regenerate, don't hand-edit). Write the domain escaped in AGENTS.md/docs too, or the guard flags the doc.
- Convio (second-opinion tooling, not a gate): `node .freebuff/convio-mcp.cjs tools` lists its skills/services, `call <tool> '<json>'` invokes one. The key lives in `.freebuff/convio-key.txt` (gitignored with the rest of `.freebuff/*`). Its useful skill here is `convio/web-security-review` — secrets, dependencies, auth, headers, hosting; its scanners are Gitleaks and Pa11y.
- Route health: `node .freebuff/route-health.cjs [--base http://localhost:4173] [--as <email>] [--only app|hub|page] [--limit N] [--json out.json] [--self-test]` drives real Chrome (`puppeteer-core`, already a devDependency; nothing is downloaded — it uses the installed browser) over all 597 study routes and fails on an in-page error card, raw exception text, or an empty page. The SPA is client-rendered, so a curl of the prerendered HTML cannot see any of that. Sweep the **built** app (`vite preview --port 4173`), not the dev server: HMR holds a websocket open so `networkidle2` never settles, and 597 routes through Vite takes >9 minutes while the preview server finishes in about five. `--as` needs `ROUTE_HEALTH_PASSWORD` and signs in first (a throwaway from `.freebuff/make-verify-student.cjs create`), and a signed-in sweep needs `ROUTE_HEALTH_CONCURRENCY=4-6`: sixteen tabs saturated the local preview server, every route read as "empty page", and a 20s `--wait` (the signed-in default) did not save it — a slow page and a broken page must not be reported the same way, so re-run a single failure at low concurrency before believing it; `--self-test` renders a missing topic and an unknown URL and asserts the classifier still flags both — re-run it after editing the patterns, because a harness that only prints PASS is indistinguishable from one that checks nothing.
- Dev server: Vite on port 8080; run doc `.freebuff/run.md`. On Windows, detach via PowerShell `Start-Process -FilePath 'npm.cmd' … -RedirectStandardOutput/-RedirectStandardError` (two different files).
- Deploy an edge function: `"$BUN" .freebuff/redeploy-manage-accounts.cjs <slug>` — multipart deploy, slug arg required, `verify_jwt: true`; add `--public` for a pre-auth function (`login-with-username`, `resolve-login-email`), where the default would make the login form itself require a token.
- Rebuild a topic's question bank against its own specification statements: `node .freebuff/build-topic-bank.cjs --topic <slug> [--apply]`, or `--all --apply --skip-applied`. It drafts through the `draft-content` function, gates and rotates the drafts, writes `.freebuff/drafts/<slug>.json` (the review artifact — read it, especially `blind_solve.items`), and only `--apply` writes. Workers AI has a **daily free neuron cap**: a full-estate run stops with `429 … used up your daily free allocation of 10,000 neurons`. Re-running with `--skip-applied` resumes; a topic whose draft file exists is reused rather than re-drafted.
- The `run_terminal_command` heredoc mangles backslashes/quotes in tricky strings; build such strings with `String.fromCharCode` or use file tools instead.
- Probes that simulate a JWT: a multi-statement `/database/query` request runs each statement in its own transaction, long `RAISE` messages come back truncated, and a caught `exception` reverts `set_config` made earlier in the same transaction — so set `request.jwt.claims` **inside** the block you assert from, keep the raised summary short, and prefer returning rows over raising.

## Database truth (critical)
- The live DB was built by direct SQL application — most of `supabase/migrations/` was never applied/recorded there. Never assume the migrations folder describes the live DB; introspect it first.
- `supabase/base.sql` is the golden full-schema snapshot (structure only, idempotent, validated by a BEGIN…ROLLBACK smoke test). After any schema change: apply live → add a migration file → regenerate with `"$BUN" .freebuff/golden-dump.cjs` (plain `node` cannot parse it: it uses top-level await) → re-smoke-test with `node .freebuff/smoke-base.cjs`.
- `frontend/src/integrations/supabase/types.ts` is hand-maintained — every new table/column/RPC must be added there manually or typecheck breaks. (The `@` alias is `frontend/src`, so `@/integrations/supabase/types` is this file; there is no `src/integrations/`.)
- `questions.statement_id` (`20261009220000`) is the only link from a question to the board statement it tests. `questions.objective_id` is a *different* thing — the per-topic teaching layer — and pointing a statement id at it violates the FK. `syllabus_coverage()` now reports `statement_questions` per row, so a topic whose whole bank sits on one of its four statements no longer reads as covered.
- `public.content_integrity_findings()` (`20261008150000`) is the admin-gated, **live-computed** content-health report behind `/admin/content-integrity`: U+FFFD in student-visible text, a `correct_option` that cannot point at the right option (0-based vs the legacy 1-based seeds), and `material_type` aliases. Extend it instead of writing another one-off content probe; its labels, order and repair links live in `frontend/src/lib/contentIntegrity.ts`.
- The damage that report hunts for is also refused at the table, not just reported: `20261009140000` adds `*_no_replacement_character` CHECKs (questions, quizzes, topics, lessons, study_materials, flashcards, flashcard_sets, past_papers, announcements) and `questions_answer_index_in_range`, and no role bypasses a CHECK the way `service_role` bypasses RLS. A console write that would store damage now fails — the copy for it lives in `frontend/src/lib/contentGuards.ts` (matched on the constraint name in PostgREST's `message`); restoring a `content_revisions` row taken before the encoding repair is refused for the same reason. Verify with `.freebuff/apply-sql-file.cjs .freebuff/probe-content-guards.sql` (dry run) and `.freebuff/probe-content-guard-live.cjs` (live, PostgREST).
- All curriculum content lives only in the live DB; seeders/exports are `.freebuff/content-*.cjs` + `.freebuff/seed-*.cjs`. There is no remote/backup yet (repo is local-only).

## Auth & security model
- `handle_new_user` (auth.users trigger, SECURITY DEFINER) seeds profile + `user_roles(role='student', is_approved=true)` and deliberately ignores client-sent role — never trust signup metadata for roles.
- Students may **change their own username** at `/settings` (`public.set_my_username`, migrations `20261022170000`/`20261022173000`): the row owner may set a canonical handle (`username_is_canonical` — lower-case, `[a-z0-9._-]`, 3–32), uniqueness is still `profiles_username_unique_idx`, and clearing a username stays admin-only because it frees the name and ends username login. The rules live once in `public.username_sanitize` (used by `handle_new_user`), `username_is_canonical` (used by the trigger and the RPC) and `frontend/src/lib/username.ts` (used by signup and the settings form). A self-service change writes a `self_service` row to `admin_audit_log`, so a released-then-claimed handle leaves a trail. A handle is displayed as `@name` everywhere, so the login form and `login-with-username` both strip a leading `@` before deciding whether the value is an email or a username (without that, typing `@sam` looked like an address and failed as one). Verified by `.freebuff/probe-username-selfservice-live.cjs` (27 checks: taken/invalid/unchanged, mixed-case direct write refused, clearing/email/owner changes refused, new handle logs in — plain, mixed-case and `@`-prefixed — and the old one stops, anon cannot execute the RPC).
- **One handle, one account — including under a race.** `profiles_username_unique_idx` is unique on `lower(username)` where username is not null, so no two students can hold `sam` and `Sam`, and a simultaneous claim is serialised by that index: two concurrent `set_my_username` calls give one `{ok:true}` and one `{error:"taken"}`, with the handle on exactly one row. Two holes sat either side of it. (1) Every identifier lookup passed the value straight to PostgREST `ilike`, and the canonical alphabet includes `_`, which SQL LIKE reads as "any single character" — measured live, a student holding `sam_1` **could not sign in** (401) because the pattern also matched `samx1`, and the raw lookup returned both rows. `login-with-username`, `resolve-login-email`, the console's duplicate checks and the parent dashboard's child-by-email lookup now escape through `likeLiteral` (edge functions) / `escapeLike` (`frontend/src/lib/username.ts`); the parent one mattered most, because the wrong match there links a stranger's child to a parent's dashboard. (2) `handle_new_user`'s EXISTS pre-check is a courtesy, not a lock: two sign-ups claiming the same handle at the same instant both passed it and the loser's INSERT escaped as GoTrue's opaque 500 "Database error saving new user". `20261022210000` retries the insert once with the id-derived suffix, so both accounts are created with distinct handles. Verified by `.freebuff/probe-username-shadow.cjs` (9 checks: the underscore handle signs in, the escaped lookup selects one row, two simultaneous claims give one winner and one `taken`, the handle stored on exactly one account) and `.freebuff/probe-signup-username-race.cjs` (run it more than once — the window is a millisecond wide). One pre-guard row still holds a mixed-case handle; the index is on `lower()`, so it cannot duplicate and every lookup is case-insensitive, so it was left alone.
- **`protect_profile_identity_fields` used to be a no-op.** It decided whether the caller was the service role with `current_setting('role')`/`session_user`, but it is `SECURITY DEFINER`, so both report the owner (`postgres`) for every caller: the disjunction was always true and the guard returned early. Measured live before the fix — a signed-in student could PATCH their own `profiles.email` (the recovery channel) and null their username through PostgREST. The fixed version keys off `auth.uid()`: a request with a `sub` is an end user, so only an admin may touch email/ownership/clearing; a service-role request has no `uid`. Same class of bug as `enforce_user_roles_writer` (see the admin lockdown entry) — never ask `current_user`/`role`/`session_user` who is calling from inside a definer function.
- Students may claim a username on the public signup form (`data.username`), so `handle_new_user` now treats that metadata as untrusted: it lower-cases, strips to `[a-z0-9._-]`, drops anything outside 3–32 chars, and suffixes a name already taken (case-insensitively) with 5 chars of the user id. That matters because `profiles_username_unique_idx` is unique on `lower(username)` and a duplicate inside the auth trigger surfaces as GoTrue's opaque "Database error saving new user" (500) — the signup would die. `login-with-username` resolves with `ilike`, so casing must never reach the table. Verified by `.freebuff/probe-signup-username-live.cjs`. Accounts are **auto-approved**: the signup approval gate was removed 2026-10-20 (policies + `is_user_approved()` + the client wall + the edge 403s, migrations `20261020080000`/`20261020081000`). `is_approved` remains only as a plan/privilege flag — `has_active_plan`'s admin exemption, approved-admin RLS reads, and the admin-only edge gates — never as an account gate.
- `auth.admin.createUser` does NOT create role rows; `manage-accounts` must write `user_roles` explicitly (past bug: panel-created admins landed as students). Its `create` action takes `role: student|parent` — a mapping that only special-cased `admin` made every "Parent" in the console a student (fixed 2026-10-22), and `role: "admin"` is now refused with 403. Passwords there are held to 12+ for admins and 8+ with lower/upper/digit/symbol for everyone else (stricter than 6+ self-signup) plus a HIBP check; the console pre-checks with `validatePassword(pw, role, 8)` so the form cannot promise less than the function enforces. `supabase.functions.invoke` throws away the function's own JSON on a non-2xx, so unwrap `error.context` (the console's `functionErrorMessage`) — otherwise every rejection reads as "Edge Function returned a non-2xx status code". Verified end-to-end by `.freebuff/probe-create-account-live.cjs`.
- **Admin access is owner-only and SQL-provisioned** (`20261022150000`). `user_roles` has no write policy for browser sessions at all — only SELECT policies (own row, parents verifying students, approved admins reading all). `enforce_user_roles_writer` refuses any insert/update/delete that touches an `admin` row once `auth.uid()` is set, and it keys off `auth.uid()` rather than `current_user`: the function is SECURITY DEFINER, so `current_user` is always its owner (postgres) and the old `current_user in ('service_role','postgres')` branch always returned early — RLS was the only real gate. The auth trigger still inserts its `student` row because it runs with no end-user JWT. `promote-admin` is deleted (source and deployment), the console has no promote/demote controls, and giving someone admin now means SQL. Verified by `.freebuff/probe-admin-lockdown-live.cjs` (9 checks: admin session cannot insert or update an admin row, student cannot self-promote, function 404, manage-accounts 403, `has_active_subscription` no longer callable by anon).
- **Admin authority needs a second factor** (`20261022180000`). A password alone signs in at AAL1, and AAL1 holds no admin power: `public.is_admin(uid)` = holds the admin role **and** `is_aal2()` (the `aal` claim of the request's access token), and every admin policy — 67 in `public`, 9 on `storage.objects` — plus six admin RPCs (`content_integrity_findings`, `syllabus_coverage`, the three paper-candidate functions, `protect_profile_identity_fields`) now ask it. The rewrite is generated from `pg_policies` and **refuses to commit** if any expression still grants admin without AAL2, so a new admin policy written the old way fails the next migration run — write `public.is_admin(auth.uid())`, never `has_role(auth.uid(), 'admin')`, in a policy. `has_role` stays pure membership. An AAL1 admin is deliberately no stronger than a student (own rows, public content, practice) so a lost phone cannot lock the owner out of the app, and the three student-facing exemption helpers (`ai_marker_quota_today`, `get_free_preview`, `get_student_questions`) still answer at AAL1. Recovery is SQL-only: `.freebuff/reset-admin-mfa.sql` (documented in `docs/admin-2fa.md`); sessions already issued keep `aal2` until their token expires (30 min). Edge functions that write with the service role cannot rely on RLS — `manage-accounts` and `generate-questions` decode the gateway-verified token and 403 with `{ code: "mfa_required" }` at AAL1. Verified by `.freebuff/probe-admin-mfa-live.cjs` (18 checks: AAL1 cannot read admin data/RPCs/write content/call the admin functions; the same calls pass after a real TOTP code, never enrolling the owner). UI: `/settings` card and the enroll-or-challenge gate in front of `/admin` (the gate, not a redirect — the owner must see they are one code away). Gitignore allows the probe through.
- **A teacher is a role *and* one subject, not a plan.** `public.teacher_subjects` (`20261029120000`) holds one row per teacher — `user_id` is the primary key, so a second subject is a constraint error — and `teacher` joins the `app_role` enum. The console creates these accounts through `manage-accounts` (admin + AAL2 only, `role: "teacher"` plus a required `subject_id`; a failed grant deletes the half-made account), and the public signup form never offers the type. Access is resolved by `frontend/src/lib/teacherAccess.ts` + `useTeacherScope` as **per subject-level**, and each gate passes `hasPaid || coversLevel(levelId)` into the same note/lesson picker a free student uses — folding a teacher into `hasPaid` would unlock the whole estate and delete the upgrade path the account exists to keep. So: the subject hub's lists and quizzes, the notes library, the note reader, the lessons index and the `/quizzes` list are full for their subject and keep the free preview + `TeacherScopeNotice` ("outside your teacher access", Upgrade) everywhere else. `useMySubjects` folds the grant's levels into `pickedIds` (a teacher is assigned a subject, not asked to pick one) and `useSubjectUnpicked` returns false for them, so another subject renders its locks instead of "add it to my subjects". An AAL1-style trap to avoid: this is a **sales gate**, exactly like the note/lesson previews — the rows are readable, and what changes is which ones the app hands over. The AI marker stays plan-only, since it is not subject content. Verified live by `.freebuff/probe-teacher-live.cjs` (8 checks: second subject refused by the PK, grant readable with its levels, grant not insertable or movable from the teacher's own session, no self-promotion) and in the browser as a real teacher account (Physics fully open across OL/AS/A2, Chemistry locked with 23 lock icons and the upgrade card, 76 quizzes listed unsliced, Settings and the dashboard naming the scope).
- **`fetchRole` reads every `user_roles` row, not one.** The PK is `id`, so a SQL-granted admin keeps the student row the signup trigger wrote; `maybeSingle()` answered that with 406 and null data, which hid the console from exactly the account that owns it (and would now hide the 2FA gate with it). Admin outranks parent, parent outranks student. `AdminRoute` also waits on `roleResolved`, because a hard reload of an `/admin/...` URL used to evaluate the guard before the role query returned and bounce to `/dashboard`.
- Edge functions run as service_role → normal audit triggers see a null actor; attribute mutations explicitly via the `audit_admin_action` RPC.
- **The legacy `anon`/`service_role` JWTs are deactivated (2026-10-30), and the app never used them.** `PUT /v1/projects/{ref}/api-keys/legacy?enabled=false` — `enabled` is a **query parameter**; a `PATCH` there, or a `PUT` with a body, answers `400 {"id": "Invalid UUID"}`. They are still listed by `GET /api-keys` but answer `401 Legacy API keys are disabled`. Everything the app touches was already modern: `.env`/`.env.production`/the **Vercel env** hold the publishable key, the served bundle carries it and no `eyJ…` literal, the function env holds `sb_secret_`/`sb_publishable_` (measured from inside a function), and the two `pg_net` cron jobs (`past-papers-harvest`, `weekly-digest`) authenticate with their own `x-harvest-secret`/`x-digest-secret` headers, not a key. Proven by `.freebuff/probe-legacy-key-cutover.cjs`: `snapshot before|after` records all 17 functions under four auth shapes (none / `apikey` / `apikey`+`Bearer <key>` / `apikey`+user token) plus the REST, RPC, storage and GoTrue paths, and `compare` prints every moved status — **NO STATUS MOVED**. `verify` (7 checks) signs up, signs in and deletes through SQL, so it needs no admin key. Two findings travel with this: (1) **the Management API's `default` secret key is not a working credential** — 401 on `/rest/v1` and `/auth/v1/admin` in every header shape, browser and non-browser UA, with legacy keys on *and* off, and its hash differs from the function env's (`548f24dd…` vs `583f28f3…`); a freshly created named secret key is rejected the same way, so admin-capable probes that create throwaway users cannot run until the platform issues a usable secret key (the SQL-catalog probes are unaffected — `probe-security-hardening` still 24/24). (2) `verify_jwt` **already** rejected the publishable key on `Authorization: Bearer` before the cutover, so the nine gated functions only ever accepted real user access tokens — the cutover removed no gate that was doing work. **The pre-cutover `verify_jwt: false` is only safe when the function answers 401 itself**, and this project's function env already holds modern keys.** Measured from inside a function: `SUPABASE_SERVICE_ROLE_KEY` is itself an `sb_secret_…`, `SUPABASE_ANON_KEY` an `sb_publishable_…`, and `SUPABASE_SECRET_KEYS` is `{"default": "sb_secret_…"}` which reads as service role — so retiring the legacy API keys needs no key-value migration in the functions, only the authorization change. `quiz-feedback` is the first migrated (`--public`, modern key resolved first with a legacy fallback, 401 for a missing *and* forged token). Do not treat `throw` as authorization: with the platform gate off it returned **500**, which reads as "retry" to a caller. Verified live by `.freebuff/probe-quiz-feedback-live.cjs` (7 checks) — note a broken service key and "no attempt" both produce 403, so the check that matters is the 200 whose branch is only reachable with a working key. Runbook: `docs/key-rotation.md`.
- Password policy: GoTrue global min length 6, `jwt_exp=1800`; admins 12+ & complexity enforced server-side in `manage-accounts`; students 6+ + complexity + HIBP k-anonymity check in `src/lib/passwordPolicy.ts`. Managed-config `password_hibp_enabled` is Pro-only (402) and the `required_characters` preset enum is broken server-side — don't retry config, enforce in code.
- **The free note preview is one note per subject-level, decided in one module.** `frontend/src/lib/noteAccess.ts` picks the level's newest `notes` row (a full note outranks a newer `summary`, which is what the first cut handed several levels) and every surface derives its lock from it: the library, the subject hub (from the level's unfiltered `materials`, so typing in search cannot change the free note), the per-topic page and the reader — the reader because `/notes/:id` is a shareable URL that would otherwise sidestep the hub. Locked rows stay listed with an Unlock link; they are the advertisement, not an error. This is a sales gate, **not** a security boundary — note bodies are readable rows and the pages are indexed, so do not present it as more than that. **Lessons follow the same shape** (`frontend/src/lib/lessonAccess.ts`): one lesson per subject-level is open and the rest stay listed with a lock, on **both** surfaces that list lessons — the subject hub and the `/lessons` index, which sliced each topic to its first lesson and folded the remainder into a "+ N more lessons" card until 2026-10-29. A locked row opens `/pricing` rather than rendering lesson content. The free lesson is the first lesson of the first topic — lesson `sort_order` alone cannot answer that, because every row in the estate carries `1` (it orders lessons *within* a topic), so the rule takes the topic's order as `topicRank`; `rankTopics` / `ranksByLevel` rank it once, so the hub and the index cannot hand out different free lessons. Both pass `hasPaid || isAdmin` — `usePlanAccess().hasPaid` is only the subscription flag, and an admin was shown locks over content they own.
- **The notes library must not fetch the estate, and must not fetch note bodies.** `fetchNotes()` selects through `topics!inner` and filters `topics.subject_level_id` to the student's picks — filtering an embedded table without `!inner` leaves every parent row in place, so the shelf was 340 rows for a 40-row student. It also drops `content`: the list only needs titles, and the reader loads its own body. Measured before/after on one level: **4,427 KB / 44.7 s cold (6.6 s warm) → 20 KB / 0.72 s**. Body search therefore moved server-side (`searchNoteIds()`, an `ilike` returning ids only, debounced 250 ms); titles and topics still filter locally and instantly. Admins keep `content` (the inline editor opens with it) — that is what `withContent` is for. Anything that adds a column to this query is adding it to every student's first paint.
- Paid features are gated *server-side*, never by the browser: `public.has_active_plan(uid)` (admin-approved OR an active, unexpired `subscriptions` row) is the one predicate. EXECUTE is granted to `service_role` only — it takes an arbitrary uid, so an authenticated grant would let anyone probe anyone else's plan. RLS policies inline the same predicate instead. `ai-correction` refuses with 403 `{ code: "plan_required", upgrade: true }`; the client turns that into the upgrade card via `isPlanRequiredError()`.
- Student answer scripts go in the private `homework-uploads` bucket at `<user_id>/ai-marker/<uuid>.<ext>`. That shape is load-bearing twice over: the bucket's insert policy requires `storage.foldername(name)[1] = auth.uid()`, and `ai-correction` refuses any `answerFiles` path outside the caller's own folder (the IDOR guard). `frontend/src/lib/answerScripts.ts` is the only place that builds those paths.

(3) `profiles`' parent SELECT was `using (i_am_parent())` — a role test, so **every parent could read every profile, emails included**; it is now scoped through `parent_student_links`, and the link form's one exact-email lookup moved into `lookup_student_for_linking(text)` (parent-only, equality not `ILIKE`, students only). ## Payments & billing
- **Stripe owns subscriptions; the browser cannot write them.** `billing` (verify_jwt true) starts Checkout and opens the customer portal; `stripe-webhook` is deployed **`--public`** and authenticates with the `Stripe-Signature` HMAC — never relax that to "accept JSON", or anyone can POST themselves a plan. The student insert/update policies on `subscriptions` were dropped on purpose (`20261028120000`); the received-receipt flow and its two `homework-uploads/payments/*` storage policies are gone. The webhook re-reads each subscription from Stripe rather than trusting the event body, so replays are idempotent.
- **A row in `subscriptions` is not a Stripe subscription, and `active` is not a claim about the calendar.** Five of the live rows carry no `stripe_customer_id`/`stripe_subscription_id` — they are plans granted by hand — and one of those says `active` with an `ends_at` three days in the past. Deciding from `status` alone produced both dead ends at once: `billing` counted any `active` row as a live subscription and refused Checkout with `already_subscribed` forever (that student could never pay again), while the UI offered those granted accounts "Manage billing", which opens the portal and answers 404 `no_customer`. The rules now live in `frontend/src/lib/subscriptionState.ts` (`comped`, `lapsed`, `hasStripeCustomer`, `liveStripeSubscription`) and `billing` re-reads any row that carries a `stripe_subscription_id` from Stripe before it blocks anything — never trust the stored `status` of a payment integration to still be true. A row without a subscription id can neither block a Checkout nor be managed, and every surface must branch on those flags rather than on `status`. Verified by `frontend/src/lib/subscriptionState.test.ts`.
- **A trial is the product.** `has_active_plan()` and `has_active_subscription()` accept `('active','trialing')`, and `ai_correction`'s insert policy is the one place that inlines the predicate — change all three together. `useSubscription` mirrors it with `ACTIVE_SUB_STATUSES`; anywhere that tests `status === "active"` alone silently locks a trialing student out.
- **The 3-day trial is one number in two places** — `TRIAL_DAYS` in `supabase/functions/billing` (Deno, cannot import from the app) and in `frontend/src/lib/legal.ts`, which the pricing page and `/refunds` both read. `/refunds` is a legal document with its own version (`REFUND_POLICY_VERSION`); its promise (full refund of the first payment when asked within 3 days) has to stay true of what the webhook and Stripe actually do.
- **`SITE_URL` is the secret Stripe sends students back to.** `billing` builds `success_url`/`cancel_url` from it, so when it still held the retired `clutch-marks.lovable.app` every Checkout redirected to a host that does not serve the app — a student who had just paid never reached `/checkout/success`. Set it to `https://clutchmarks.study` and verify by reading a real session's `success_url` (`GET /v1/checkout/sessions/{id}`), not by reading the function's output.
- **Never set `payment_method_types` on a Checkout Session.** Stripe now rejects it outright (`The payment_method_types parameter is no longer supported…`, yet another reminder that the API changes under this integration): methods come from the Dashboard's dynamic set. Dropping it did not lose Apple Pay — Apple Pay is a wallet inside card and still appears automatically — and card is enabled on the account. Restrict methods with a payment-method configuration in the Dashboard, not in code.
- **Adaptive Pricing is on, deliberately — so Checkout quotes local money, not the site's USD.** `billing` sends no `adaptive_pricing`, and Stripe's account setting presents the customer's local currency: the $20 monthly plan rendered **SAR 78.06** to a Saudi customer, which is 3.903× the 3.75 SAR peg — the 2–4% conversion fee Stripe charges is paid by the student. Every surface quotes USD from `plans`, so for a non-US visitor the Checkout number will not equal the number on /pricing; that gap is the accepted trade (local payment methods such as Klarna and Amazon Pay require local presentment). If it ever has to match exactly, the switch is a Checkout parameter, not a Dashboard-only setting: `adaptive_pricing[enabled]=false`, measured rendering exactly `$20.00`. The session's own `currency`/`amount_total` stay USD either way, so reading them proves nothing — open the hosted page.
- **This project runs on a live key only.** A `sk_test_` key cannot charge the live Prices in `plans.stripe_price_id`, and a test subscription written by the webhook would grant real access because `subscriptions` has no mode column. Test mode was tried and removed on 2026-10-28. The installed key is a live **restricted** key (`rk_live_…`): it works if it carries Prices read, Checkout Sessions write, Customers write, Subscriptions read, Billing Portal write and Webhook Endpoints write. Stripe escalates subscription **writes** from it to a human-approval request; harmless, because the app only reads subscriptions and cancellation goes through the customer portal. Catalog ids, the live webhook endpoint and the portal configuration id are in `docs/infrastructure.md`.

- **Past papers are linked to the board, never served — and reading them is free.** Every card on `/past-papers` and on each per-topic papers page sends the reader to the board's own page for that qualification (`officialPaperPage` in `frontend/src/lib/pastPaperFiles.ts`, keyed `subject/LEVEL/board` because Physics AS is Cambridge 9702 for some rows and Edexcel IAL for others; it never returns a non-board domain, so a mirror cannot be linked). Redistributing board papers is a copyright problem, not a paywall, so there is deliberately **no view/download button and no watermark path**: `serve-material` refuses the `past-papers` bucket to non-admins (`403 board_link_only`), `serve-external-paper` is no longer called by the app, and the plan gate sits only on the AI marker ("Submit for marking"). `paper_url` / `mark_scheme_url` stay in the table for admin tooling and the marker's server-side grounding — do not re-expose them. A row with no `paper_url` is therefore normal, not broken: Biology, Chemistry and both English qualifications are catalogue-only, seeded by `.freebuff/seed-past-papers-bio-chem-eng.cjs`, which is idempotent on title + year + session. Conversely, an `INSERT`/`UPDATE` through the Management API answers `201` whether it matched zero rows or not — assert the count afterwards (`select length(content)`, `select count(*)`), never the status code. `docs/past-papers.md` holds the inventory.
- **The paper desk is a briefing, never a viewer.** The per-topic papers page renders `PaperDesk` (`frontend/src/components/PaperDesk.tsx`): the sittings as a list, the chosen paper's briefing beside it (sticky at ≥ `md`, expanded inline under the row below it), newest first — `relatedTopicPapers` concatenates two query results, so the list needed sorting or five identical titles arrived in arbitrary order. The pane may hold only our own work: the board-page link, Submit for marking, and the bridge into the topic's notes and questions. A board PDF in that pane — the blueprint's "synchronized split-pane viewer" taken literally — is the copyright line above, not a paywall. Archive search is tokenised (`frontend/src/lib/pastPaperSearch.ts`): every space-separated word must match some field, topic/subject/level included, and the same tokens drive the `Highlight` marks, because a row that filters in must be the row whose matches are visible — "2024 chem" went from 0 rows to 12 that way.
- **The mobile sidebar is a Radix `Sheet`, and nothing closed it.** Tapping a nav item navigated and left the 288 px panel covering the page, so the menu read as broken. `AppSidebar` now closes it on `pathname` change (`useSidebar().setOpenMobile`). Any new nav entry added to that sheet inherits the fix; a route change is the trigger, not the click.
- PostgREST embed `topics(name)` returns 400 if the FK is missing — embeds require real FKs (`flashcard_sets` lost its FK once and every list query 400'd).
- Generic PL/pgSQL triggers spanning multiple tables: `NEW.name` throws at runtime on tables without that column (broke announcement inserts with an unhelpful 400) — use `to_jsonb(NEW)->>'field'`.
- `pg_get_functiondef` output ends with a bare `$function$` line (no semicolon) — concatenating emitted SQL without terminating produces confusing downstream syntax errors.
- `ai_audit_log.action` has a CHECK constraint. `ai-correction` writes `'paper_correction'`, which the original constraint (`plan`,`correction`) rejected — every audit insert failed silently for months while the function reported success. When adding a new audit action, migrate the constraint in the same change (fixed for `paper_correction` by `20261008140000`).
- **A contact route is one literal: `SUPPORT_EMAIL` in `frontend/src/lib/support.ts`.** `site.ts` re-exports it as `SITE.supportEmail`; the legal notice, data-rights page, footer, sidebar, 404, crash boundary, settings note, 2FA reset copy, feedback form/dialog and the AI Marker's failure line all read the shared constant. `frontend/src/lib/email-config.test.ts` fails if any other file in `src`/`frontend/src` hard-codes the address, and it now reads the **deployed** function tree (`supabase/functions/...`) — the `backend/supabase/functions` copies are stale and a guard pointed at them proves nothing about what ships. The two outbound emails (`welcome-email`, `weekly-digest`) set `reply_to: SUPPORT_EMAIL` as well as printing it, because the sending identity (`onboarding@resend.dev` / `no-reply@`) is not a route anyone reads.
- `login_lookup_throttle` table + `register_login_lookup` RPC back the `resolve-login-email` rate limiter; if the RPC is missing the limiter silently no-ops.
- `user_roles` PK is `id` only (no unique on `user_id`) — role rows can duplicate; admin checks use `.eq("role","admin").eq("is_approved",true)`.
- **Every edge function must call `Deno.serve(handler)`** (or export a default fetch handler). With only `export async function handler` the deploy still reports ACTIVE but the function is never dispatched: invocations hang with *no log entry at all* until the platform kills them at ~150s (opaque 504/546). `study-planner` shipped that way and had never worked.
- **No student could submit a quiz**, twice over, and both faults only appear when the RPC actually runs. `grade_quiz` still called `public.is_user_approved()` after the approval gate was dropped (`20261020080000`), and it stored the inserted attempt's uuid in `_selected integer`, the variable that holds an option index — so `returning id into _selected` raised `invalid input syntax for type integer` even once the first fault was gone. `check_practice_answer` carried the same stale guard. - **Queueing a flashcard pays XP, because the trigger is on INSERT.** `xp_flashcard_review` is `AFTER INSERT ON flashcard_progress` and calls `award_xp(uid, 'flashcards', card_id, 5, 40)` (5 points, **40/day per tool**), while the review UI (root `src/pages/Flashcards.tsx` — the app entry is `/src/main.tsx`, and `@` resolves to `frontend/src`) *updates* an existing row when a card is rated. So the XP event means "a card entered your queue", not "you reviewed it": anything that pre-inserts progress rows — phase 3.4's marking queue does, at `interval_days = 0` — spends that day's flashcard allowance up front and the review that follows earns nothing. Bounded at 8 cards = 40 points/day, which is why the queue caps at `MAX_CARDS_PER_MARKING = 12` per paper rather than one card per missed point. Related: **`profiles` carries two uuids** and only one is the account. `profiles.id` is the profile's own row id; `profiles.user_id` is the auth uid and the sole FK target (`profiles_user_id_fkey` → `auth.users(id)`, 60/60 join on it, 0 on `id`). `flashcard_progress.user_id`, `xp_events.user_id` and every edge function's `user.id` are the **auth uid** — writing a `profiles.id` there fails the FK, which is how the 3.4 probe first failed.
- **A withheld mark can be claimed, and the claim itself is the audit trail.** Phase 3.2: every MISS in the checklist carries a "My phrasing is equivalent" action; submitting it writes `mark_disputes` and the mark counts in the panel immediately — "award and flag" — while the marker's own record (`ai_correction.corrected_papers`) is never rewritten. `/admin/mark-disputes` is where an admin upholds or rejects. One claim per point per marking — a unique index on `(user_id, audit_ref, md5(question), md5(point))`, because the raw text can exceed the btree entry limit — reason 10–1000 chars, U+FFFD refused, and a resolved row must carry `resolved_at` + `resolved_by`. Verified by `.freebuff/probe-mark-disputes.sql` (9 properties, rolled back: own=1 others=0 self_upd=0, AAL2 admin sees 2 and resolves 2, spoofed user_id / duplicate point / short reason / U+FFFD all blocked).
- **English is marked on band descriptors, and English is two regimes, not one.** Phase 3.3: every other subject is point-marked (M1/A1), and the marker's prompt was built entirely around that, so a 0500 composition was being asked for method marks it does not have. `supabase/functions/ai-correction/englishMarker.ts` (pure, imported by `frontend/src/lib/englishMarker.test.ts`) now decides the regime from the **subject row server-side** (`isEnglishSubject`, slug prefix `english`, name fallback): reading questions (comprehension, "give two reasons", summary by content points) stay point-marked, writing tasks (directed writing, composition, 9280 writing) return `criteria` — name, band, `marks_awarded`/`marks_available`, descriptor, quoted evidence, next step — and the prompt forbids M1/A1/B1 on a writing task. Both English qualifications are **catalogue-only: 30 papers, 0 mark schemes**, so `loadMarkScheme` is skipped for English and the descriptors travel in the prompt instead (`mark_scheme.loaded: false` is the correct answer there, not a failure). Three rules are load-bearing. (1) **The totals are the board's, never the code's** — `reconcileBand` only checks that the criteria add up to the paper's own question total and rescales proportionally when they do not; no weight is hard-coded. (2) **A placed band with no marks under it is not a 0-mark script** — measured live, the model sent Band 2 with every criterion at 0, i.e. a 0/25 composition; `fallbackEarned` (the question-level mark) is now shared across the criteria in proportion to their maxima and flagged `derivedFromQuestion`. Verified live by `.freebuff/probe-english-marker-live.cjs` (27 checks, one Gemini call, throwaway funded student it deletes: marks a real 0500/22 composition, then asserts the regime, criteria summing to 25/25, no M1/A1 language, quoted evidence on every placement, a band placement carrying marks, the review queue, and the stored row + audit entry) plus 14 unit tests. **Now calibrated against the boards' own examiner-marked exemplars** (`docs/english-marker-calibration.md`, harness `.freebuff/calibrate-english-marker.cjs`, 13 scripts / 26 live markings, 2026-10-30): the criteria it returned for 9280 were **not the board's at all** — a three-way "Content / Organisation / Accuracy" split it invented, 16/16 placements unmatched and no `Language` criterion for language marks to land in, which pushed the best scripts to 5/16 and 15/23. ## Content conventions
- **OxfordAQA 9202 Chemistry is phase 4's first non-Cambridge science, and it is deliberately hidden.** `chemistry-oxfordaqa` / IGCSE exist with **10 topics and 30 syllabus statements parsed from the official specification v6.2** (not retyped; the two headings the spec prints in odd casing are sentence-cased), but both the subject and its level are `is_active = false` and nothing has been added to `topicManifest.generated.ts`, so the catalogue, sitemap and subject picker do not mention it. Content pipeline: `node .freebuff/seed-oxfordaqa-9202.cjs [--apply]` (idempotent on slug / (subject_id, level) / (subject_level_id, slug) / (board, spec_code, code)), notes in `.freebuff/content-oxfordaqa-9202-*.cjs` written by `node .freebuff/seed-oxfordaqa-9202-notes.cjs --apply` (upsert on `(topic_id, title)`, so a re-run updates rather than duplicating). Two of ten notes are at the bar. **The content audits filter on the subject *name***: `gate-notes-depth.cjs chemistry-oxfordaqa IGCSE`, `audit-note-formulas.cjs OxfordAQA`, `audit-answer-steps.cjs OxfordAQA` — passing the slug audits nothing and prints a clean `0 materials`, so check the material count, not just the verdict. `docs/oxfordaqa-9202.md` lists what remains before activation (8 notes, question bank, papers, manifest/copy/SEO).
- **An equation is written with symbols, and every symbol is defined.** The standard is a real glyph — Δ, λ, ρ, σ, ω, θ, ε₀, μ₀, π, √, ⇌, →, ², ³, ⁻¹ — never the English name: `p = rho g h`, `E = m c delta theta` and `v = f lambda` were all live in the Physics notes, inside `<pre><code>` blocks, and a student reading the body met the spelled form. Each equation carries an `<em>Key:</em>` line *inside the same `<p>`*, naming every symbol with its unit ("p = pressure (Pa); ρ = density (kg/m³); h = depth (m)"). Comparison operators are escaped glyphs (`&lt;`, `&gt;`), not "(less than)". The audit is read-only and covers notes, summaries and lessons: `node .freebuff/audit-note-formulas.cjs [subject] [--json out.json]`, which also lists spelled-out Greek and formula lines with no key. Sections are **appended**, never rewritten: `.freebuff/append-note-sections.cjs <module>` builds `content = content || section` guarded by id, `material_type` and a heading check, and `.freebuff/apply-note-text-fixes.cjs <module>` repairs a spelled symbol in place through an exact-string replacement that must match. Physics IGCSE's ten notes are at the bar (10/10 clean, 115 keyed equations), the five worst AS/A2 Physics notes joined them (118 keyed equations; Physics AS and A2 are 16/28 clean, all at the depth bar), and a first section each for Mathematics, Chemistry, Biology, Computer Science and both English specifications followed (81 more equations). The estate is 480 of 480 clean (340 notes/summaries + all 140 lessons), with 2,932 relations counted and a `<em>Key:</em>` on every row that carries one.
- **The audit's relation rule had to learn what is *not* an equation, and `--self-test` proves it still bites.** It originally counted any `=` line, so it reported a table's own `<table border="1">` attribute, SQL in a `<pre>` block, a method call and prose like `HTTPS = HTTP over TLS` as "formula lines but no symbol key" — 14 lesson rows that could only be "fixed" by keying nonsense. The rule now strips markup, requires a formula-shaped right-hand side (number, glyph, bracket or single letter after the `=`), skips a `<pre>`/`<code>` span *including its continuation lines* (a block only opens the tag on its first line), skips SQL clauses written inside prose, and skips a tautology (`1=1`). A reaction is also an equation: `2K + 2H₂O → 2KOH + H₂` counts, but only when chemical evidence (an element symbol with a count, or a subscript) sits within 24 characters of the arrow, because English prose uses arrows too (`QUOTATION → METHOD`) and a translation pipeline is not a reaction. "Mentions equations but writes none" no longer fires on a row that already carries a key or writes `CₙH₂ₙ`. `node .freebuff/audit-note-formulas.cjs --self-test` runs 17 positive and negative cases, including three lines that must be rejected; re-run it after editing the rule.
- **English has no formula sheet, and the audit already said so — the content did not.** An earlier pass appended an `<h2>Equations and symbols</h2>` section to four English notes (Prepositions and Collocations, Word Formation, FLL Analysing Language Choices, ESL Writing Tasks), framing method structures as `writer's effect = feature + connotation + reader response` with an `<em>Key:</em>` gloss under each. The audit exempts English (`EQUATION_FREE`), so nothing flagged it. `.freebuff/strip-english-formulas.cjs` rewrites those four sections as method sections — a subject heading (`The mapping rules, one page`, `Derivation patterns, one page`, `Structures the mark scheme rewards`), the `=` read as `is` (an em dash inside a bold structure line), each gloss on its own `<br>` — and it refuses to write while any ` = `, `<em>Key:</em>` or heading survives, while an h2/h3 is added or removed, or while the tag balance shifts by anything other than the removed `<em>` pairs. It transforms the **originals**, kept in `.freebuff-tmp/english-formulas-snapshot.json`, so a second run corrects the first instead of stacking; verify with `select count(*) filter (where content ilike '%Equations and symbols%') from study_materials` for the English subjects (must be 0).
- **A second, rule-based normaliser handles bodies whose notation is systematically wrong**, which hand-written pairs cannot: `.freebuff/normalise-note-notation.cjs` turns spelled Greek into glyphs, `6.63 x 10-34` into `6.63 × 10⁻³⁴` (the old form read as *ten minus thirty-four*), `m s-1` into `m s⁻¹`, `sqrt(` into `√(`, `->` into `→`, `deg C` into `°C`. A price change is: update the row → regenerate → commit the generated file. `node scripts/generate-plans-manifest.cjs --check` compares the committed snapshot with the live table and is the first step of `npm run verify` (exit 1 on drift, with the differing plan lines printed; exit 2 when no token is available, which `verify` passes only because it passes `--allow-unavailable`, and then says NOT CHECKED out loud). The snapshot exists because /pricing is prerendered and the build must not query Supabase; `frontend/src/lib/plans.test.ts` fails if a surface quotes a number the snapshot does not contain. Never restate a price in `plans.description` — that is how the page came to say $40/month while the table said $20, and $80/year while it said $60.
- Brand assets (`public/icon-*.png`, `favicon.ico`, `og.png`, `brand/*`, `site.webmanifest`) are generated by `.freebuff/build-brand-assets.cjs` from the owner's artwork — regenerate, never hand-edit. Resize first, apply the rounded mask last: sharp doesn't premultiply, so masking before resizing rings pink/yellow along the alpha edge. `BrandMark`/`BrandLockup` render `brand/mark-512.png` (logo tile above the wordmark band).
- PDF toolchain: `.freebuff/pdftool/` (own package.json, pdfjs) with local PDFs in `out/`; scripts `build-materials.cjs`, `build-booklet-splits.cjs`, `build-previews.cjs` — re-run after re-splitting. Uploaded files live in storage, not the repo.
- AI features: `ai-correction` marks papers through the **Gemini API** by default (`GEMINI_API_KEY`, model `GEMINI_MODEL`, default `gemini-3.5-flash-lite` (`gemini-3.8-flash` hit zero free-tier quota on the live key); key sent in the `x-goog-api-key` header). Set `AI_PROVIDER=cloudflare` to fall back to Workers AI (`CLOUDFLARE_API_KEY` + `CLOUDFLARE_ACCOUNT_ID`). `study-planner`, `generate-questions` and `quiz-feedback` use that same Gemini key — every `LOVABLE_API_KEY` reference and the `ai.gateway.lovable.dev` calls were removed 2026-10-28, along with the `lovable-tagger` dev plugin that drew the "Edit with Lovable" badge. With no key at all the planner serves a deterministic offline plan rather than ever returning a 504.
- `ai-correction` is deployed and plan-gated (see Auth & security model). It marks typed answers, photos of a handwritten script (Gemini reads images in one multimodal call by default; on the Workers AI fallback, `VISION_MODEL_CANDIDATES` is tried in order and the winner is cached per isolate; verify with `.freebuff/probe-ai-correction-live.cjs`) and PDFs — on the Gemini path a PDF is sent **whole** (`inline_data`, `application/pdf`; Gemini renders the pages, so *scanned* scripts with no text layer mark fine — the in-function text extractor that used to return "" for scans, forcing a 422, now serves only the Workers AI fallback and mark-scheme grounding). Raw inline bytes are capped at 14 MB (`MAX_INLINE_TOTAL_BYTES`) because base64 inflates 4/3 and Gemini's per-request ceiling is 20 MB. Re-run `node .freebuff/probe-ai-correction-live.cjs` after any change to it: it asserts the gate, upload isolation and both marking paths against the live project with throwaway accounts; `node .freebuff/probe-ai-scan-pdf.cjs` is the one-off check that a scanned PDF (image-only page, no text operators) still marks.
- Workers AI rejects retired/short model names outright ("No such model"; `llama-3.1-8b-instruct` died 2026-05-30). Both functions keep an alias map — send `@cf/…` ids or nothing and let the worker resolve.

## User preferences
- Notes must be exam-grade and syllabus-referenced, not simplified "explain-like-I'm-5" style.
- SaveMyExams-like UX: per-topic pages with SEO-friendly slugs (`/study/:subject/:level/:topic/notes|quiz|papers` via `src/lib/topicUrls.ts`); minimize clicks to reach anything.
- Security is the user's top concern (account takeover destroying content/reputation) — prefer defense in depth and verify changes live instead of assuming.
